# وائم WAEM 360° — مشروع موحّد وجاهز لـ GitHub

تم دمج **ملف MVP المرحلة الأولى** مع **ملف P0 لإدارة الاشتراكات** داخل مستودع واحد، مع إعداد نشر الواجهة تلقائيًا على GitHub Pages.

## مكونات المشروع

| المسار | المحتوى | النشر |
|---|---|---|
| `src/`, `public/`, `prisma/` | واجهة وائم Next.js: لوحة القيادة، المستخدمون، صفحة health، مخطط Prisma | الواجهة الثابتة تُنشر على GitHub Pages |
| `services/subscriptions-api/` | خدمة Express + PostgreSQL لإدارة المؤسسات والباقات والاشتراكات والفواتير والمدفوعات اليدوية والتذكيرات وسجل التدقيق، مع اختبارات منطق المجال | محفوظة في GitHub وتحتاج خادمًا مستقلًا لتعمل |
| `services/next-server-reference/` | نسخة مرجعية من مسار Next.js API الصحي الأصلي غير الممكن نشره على Pages | مرجع فقط |
| `.github/workflows/deploy-pages.yml` | اختبار منطق الاشتراكات وبناء الواجهة ونشرها تلقائيًا | GitHub Actions |

> **مهم:** GitHub Pages يستضيف مواقع ثابتة فقط. لا يمكنه تشغيل Express أو PostgreSQL أو Next.js API routes. وجود ملفات الـ API في المستودع **لا يعني أنها تعمل على رابط GitHub Pages**. ولا يوجد ربط إنتاجي بين الواجهة وخدمة الاشتراكات حتى الآن. كذلك مخطط Prisma للواجهة ومخطط SQL لخدمة الاشتراكات مستقلان ويحتاجان قرارًا هندسيًا بشأن التوحيد قبل بناء نظام إنتاجي.

## الرفع والنشر على GitHub (بدون خادم)

1. أنشئ مستودعًا جديدًا (مثل `waem-360`) في GitHub.
2. **فك الضغط** وارفع محتويات هذا المجلد إلى جذر المستودع على فرع `main`؛ يجب أن يكون `package.json` و`.github/` في الجذر. لا ترفع ملف ZIP وحده.
3. افتح `Settings → Pages` واختر `GitHub Actions` ضمن `Build and deployment`.
4. افتح تبويب `Actions` وتابع `Deploy WAEM to GitHub Pages`، أو شغّله يدويًا من `Run workflow`.
5. افتح رابط `https://USERNAME.github.io/REPOSITORY/` بعد نجاح التنفيذ.

مسارات الواجهة المنشورة: `/` و`/users/` و`/health/` (تُضاف بعد اسم المستودع). صفحة المستخدمين تعمل كتجربة باستخدام `localStorage` في نفس المتصفح ولا تحتوي مصادقة حقيقية.

## تشغيل الواجهة على جهازك

يتطلب Node.js 22 أو إصدارًا متوافقًا، ثم:

```bash
npm install
npm run dev
```

افتح `http://localhost:3000`. ولإنشاء ملفات الواجهة الثابتة محليًا:

```bash
npm run build
```

ستجد الملفات داخل `out/`. لا يحتاج عرض الواجهة وحده إلى PostgreSQL.

## تشغيل خدمة الاشتراكات على جهازك/خادم منفصل

تتطلب **PostgreSQL** وNode.js، ولا تعمل على GitHub Pages.

```bash
cd services/subscriptions-api
npm install
npm test
cp .env.example .env
# عدّل DATABASE_URL وADMIN_API_KEY إلى قيم آمنة
psql "$DATABASE_URL" -f schema.sql
npm run dev
```

الخدمة تستمع افتراضيًا على المنفذ `3000`، لذلك إذا شغّلت Next.js وExpress على الجهاز نفسه غيّر `PORT=3001` في ملف `.env` لخدمة Express. كل طلبات `/api` تتطلب الترويسة `x-admin-api-key`.

للدراسة، راجع `services/subscriptions-api/README.md` للحصول على تفاصيل المسارات وحدود الأمان والضرائب. مفتاح API الإداري الحالي آلية تطوير فقط، ولا يُكتب في كود الواجهة أو GitHub Pages. **لا تنشر أو تستخدم معلومات مالية أو بيانات عملاء حقيقية** قبل تطوير الصلاحيات والمصادقة والحماية والامتثال.

## فحص النشر

تُشغّل GitHub Actions اختبارات `services/subscriptions-api/tests/` وتبني Next.js في وضع التصدير الثابت. إعداد `basePath` يتكيّف مع اسم المستودع. لا توجد إعدادات أسرار مطلوبة للواجهة التجريبية.

## الحالة الحالية

- ✅ تم الحفاظ على صفحات MVP وإعداد GitHub Pages.
- ✅ تم إضافة مشروع P0 كاملًا (API، قاعدة SQL، الاختبارات، توثيق البيئة).
- ✅ تم دمج المشروعين في **مستودع واحد** مع اختبار خدمة الاشتراكات أثناء النشر.
- ⚠️ الخدمة الخلفية لا تُنشر إلى GitHub Pages؛ تشغيلها يحتاج استضافة PostgreSQL وNode.js مستقلة.
- ⚠️ الواجهة غير مربوطة بالـ API الحقيقي، ولم يتم توحيد مخططي البيانات.
- ⚠️ المشروع نموذج تطوير، وليس نظامًا ماليًا إنتاجيًا أو نظام فواتير متوافقًا مع ZATCA.
